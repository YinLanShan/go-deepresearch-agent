# 项目深度复盘（STAR 版）

> 主项目 · 用于简历与面试主讲
> 代码量：生产 10781 行 / 测试 8242 行（43%）· 247 个测试函数 · 17 个包 · 67 个 PG 集成测试 · 37 次提交

---

## 一、一句话概括

**一个面向"长周期、多子任务、可中断"场景的多智能体深度研究系统。**
它不是一个问答机器人——用户给出研究目标后，AI 会自主拆解、并行调研、多轮汇总，
一次研究可能持续数十轮，中间涉及多个并发子任务，随时可能被用户打断再继续。

真正的难点不在于"调用大模型"，而在于**让一个长时间运行的分布式系统在状态上始终正确**。

---

## 二、S：背景与问题（为什么要做）

### 2.1 起点

主流 Agent 实现（含多数开源框架的默认范式）是**一次性的**：
输入一个 prompt，跑一个 ReAct 循环，输出答案，结束。

但"深度研究"这个场景天然不是一次性的：

| 现实需求 | 一次性 Agent 的问题 |
|---|---|
| 研究要分多轮推进 | 每轮都要重建上下文，历史丢失 |
| 子任务要并行执行 | 串行执行，10 个子任务就是 10 倍耗时 |
| 用户可能中途补充需求 | 无法插队，只能等当前轮跑完 |
| 用户可能取消某个子任务 | 没有撤销概念，只能整体重来 |
| 进程重启后不能全丢 | 内存态，重启归零 |

所以第一件事是**换掉执行模型**：从"一次性 Runner"改成"长期存活的 TurnLoop"。

> 技术选型：CloudWeGo Eino 的 `adk.TurnLoop`（支持 `GenInput` / `GenResume` /
> `Preempted`），而不是 `adk.Runner`（一次性执行到结束）。
> 这是整个架构的地基——选错就没有"多轮 + 可打断"。

### 2.2 三个真正难的地方

换掉执行模型之后，冒出三类问题，这才是项目的主要挑战：

**难点一：状态语义的模糊性**

什么叫"这轮结束了"？什么叫"整个研究结束了"？

如果混为一谈，会出现一个隐蔽但致命的 bug：
模型说完一段话、派发了子任务，然后"没话说了"——
系统认为研究结束，退出循环，**子任务的结果再也没有人来汇总**。

**难点二：并发下的正确性**

子任务并行执行后，出现了多个"同时发生"的场景：

```
场景 A：模型撤销 assignment-1 的同时，assignment-1 正好执行完提交结果
场景 B：多个子任务同时提交结果，聚合器如何保证不丢、不重、不乱序
场景 C：全局中止的同时，队列里还有 Work 在排队
```

没有一处是"写个 if 就能解决"的，都需要先定义清楚顺序语义。

**难点三：数据不丢**

研究过程中产生的证据、过程记录、结论、撤销记录，都必须能持久化，
且换数据库不能改变行为。而研究状态的数据结构有 6 个变长集合，
其中"证据（Results）"还必须支持**按子任务精确删除**（因为要撤销）。

### 2.3 目标（Task）

用一句话定义要达成的标准：

> **让一个可能运行几十轮、涉及多个并发子任务、随时可被打断的 Agent，
> 在状态、并发、数据三个维度上始终正确，并且这些正确性可以被测试锁定。**

具体拆成 4 个可验收的目标：

1. 状态机语义无歧义：明确区分"本轮结束"与"研究结束"，且两种情况下系统行为正确；
2. 并发场景有确定语义：撤销/提交/中止的竞争窗口有明确优先级且不可违背；
3. 错误可感知可分级：失败不能静默，但也不能刷屏；
4. 数据可持久化且行为不变：内存与 PostgreSQL 两套实现语义完全一致。

## 三、A：实现（关键技术决策与做法）

下面 5 块是项目的技术主体。每块都按 **问题 → 决策 → 验证** 组织。

---

### 3.1 状态语义：把"结束"拆成两种

**问题**：模型"暂时没话说"和"研究真的做完了"，在事件流上几乎无法区分。

**决策**：引入两个显式状态，并且只允许一种方式进入终态：

| 事件 | 判定依据 | 系统行为 |
|---|---|---|
| **本轮结束** | 模型返回但未调用 `finish_research` | RunTask 保持 `running`，Loop 存活，等待被唤醒 |
| **研究结束** | 模型主动调用 `finish_research` | 取消全部子任务 → 关闭提交门控 → 写结论 → 进入终态 |

关键约束：

- `finish_research` **不可逆**，模型不能"反悔"；
- 它**无论子任务处于什么状态都全部取消**（包括正在跑的）；
- 本轮结束**不产生任何新状态**，只是"回到空闲"。

**为什么这是核心优势**：这是一个**设计判断**而不是编码技巧。
大多数实现把"模型这轮说完了"当成结束，代码能跑、demo 能演示，
但一到"派发子任务后等待"的真实场景就崩。

---

### 3.2 两种唤醒机制（这里踩过一个真实 bug）

**问题**：Loop 进入空闲后，谁来叫醒它？

最初只实现了**结果提交唤醒**：子任务提交结果时，若 Supervisor 空闲则唤醒。
听起来够用了——直到跑真实路径时发现：

> **如果所有子任务都失败了（或都被取消了），没有任何"结果提交"，Loop 永远醒不过来。**

系统就停在那里，RunTask 一直是 `running`，用户一直等。

**决策**：增加第二种唤醒——**子任务全部终结唤醒**。

```
wakeOnSettled：当某 RunTask 下所有 Assignment 都进入终态
              （completed / failed / cancelled）时唤醒 Supervisor
```

并用 `settledWoken` 去重，避免撤销/失败连续触发时反复唤醒同一次空闲期。

两种唤醒的职责差异：

| 唤醒类型 | 触发条件 | 语义 |
|---|---|---|
| 结果提交（抢占） | 有子任务成功提交 | "有新信息，来汇总" |
| 全部终结 | 所有子任务到终态 | "别等了，该收尾了" |

**验证**：`maybePublishSettled` 覆盖 5 条终态退出路径
（完成 / 失败 / 取消 / 超时 / 槽位失败），每条都会检查是否"全部终结"。

---

### 3.3 并发正确性：撤销与提交的竞争窗口

**问题**：撤销和提交可能同时发生。

```
goroutine A: 模型调用 cancel_assignments 撤销 assignment-1
goroutine B: assignment-1 的 Work 刚好执行完，正在提交结果
```

如果校验顺序写反（先查"这个 assignment 还活着吗"，再标记撤销），
B 可能抢在标记之前提交成功，撤销就失效了——**数据里会留下一个已被用户撤销的证据**。

**决策：先标记状态，然后判断拦截。**

```
1) 先无条件把 assignmentID 写入"撤销门控"（revoked 集合）—— 谁先到都记下来
2) 提交侧在锁内检查：该 assignmentID 是否在撤销集合中
   - 在 → 丢弃这次提交，并上报"已撤销"
   - 不在 → 正常提交
```

顺序不可颠倒：**标记发生在校验之前**，所以无论 B 多快，只要 A 开始执行，
B 之后的提交一定会被拦下。

**配套机制**：

| 机制 | 作用 |
|---|---|
| 撤销门控（二级索引 `runTaskID → assignmentID`） | 支持"整个 RunTask 被中止"时批量判定 |
| 结果槽位（ResultSlots） | 提交前必须已完成 `Reserve`，撤销时 `Revoke` 打墓碑 |
| tombstone 槽位 | 撤销的槽位不删除、只标记 `Committed`，避免"撤销后又被重新占用" |

**验证**：撤销后前端只收到一条 `cancelled`，不再有阶段倒退的事件。

---

### 3.4 真并行：从"假并行"到工厂模式

**问题**：WorkPool 最初是"共享一个 Worker 实例"。

看起来有 N 个执行槽位，实际上：

- 所有 Work 共享同一个 Worker 对象；
- `WorkerID` 互相覆盖；
- 取消一个会影响到其它；
- **并发是假的**。

**决策**：改为**工厂模式**——每个 Work 创建一个独立的子 Agent。

```go
type WorkerFactory func(w *domain.Work) (Worker, error)
```

每个子 Agent 有自己的：

- 独立的 `ChatModelAgent` 实例（互不干扰对话历史）；
- 独立的取消 `context`（取消一个不影响另一个）；
- 独立的工具白名单（**过滤掉控制类工具**）。

**一个重要的边界决策：子 Agent 不需要审批。**

最初子 Agent 也走审批中间件，但子任务是后台自动执行的，旁边没有人在点"同意"。
现在子 Agent 完全不注入审批中间件：

```go
subAgentForbiddenTools = {submit_assignments, cancel_assignments, finish_research}
```

控制类工具只属于 Supervisor，子 Agent 只拿业务工具。
**超时直接终止，且不提交结果**（避免"半成品证据"污染研究状态）。

**验证**：并行执行的 Work 有各自的 `worker_id`、各自的起止时间，互不覆盖。

---

### 3.5 背压：两级并发控制

**问题**：如果模型一次派发 20 个子任务，全部立刻创建 Work，会瞬间打满资源。

**决策**：两级计数，职责分离：

| 参数 | 计数范围 | 作用 |
|---|---|---|
| `MaxConcurrency`（Scheduler） | **在途**（排队 + 执行） | 背压：超出则排队，不创建 Work |
| `Workers`（WorkPool） | **正在执行** | 限流：真正并行的子 Agent 数 |

两者必须满足 `MaxConcurrency >= Workers`，否则部分 Worker 永远闲置——
启动时检测并告警。

**为什么需要两个**：只有 `Workers` 时，模型派发 20 个就会立刻创建 20 个 Work 对象
（只是排队等待），内存与状态管理成本照样上去。`MaxConcurrency` 才是真正的闸门。

### 3.6 错误处理：两个正交维度

**问题**：项目的错误分散在 10 个包里，现状是：

- 43 处原生 `errors.New` / `fmt.Errorf`，无法统一判断；
- **45 处 `_ =` 静默丢弃**错误；
- **38 处 `slog.Error` 后继续执行**；
- API 层 20 处直接把 `err.Error()` 返回给客户端（泄漏内部细节）。

**决策：错误分层，且"层级"与"严重度"是两个正交维度。**

| 维度 | 取值 | 回答什么问题 |
|---|---|---|
| **Layer** | infrastructure / work / scheduler / result / runtime / api | 谁该处理？ |
| **Severity** | info / warning / error / fatal | 该不该打扰用户？ |

核心机制是**幂等 Wrap**：

```go
func (b *Builder) Wrap(err error) *Error {
    var existing *Error
    if errors.As(err, &existing) {
        return existing      // 已包装过 → 原样返回
    }
    b.e.Err = err
    return b.e
}
```

**为什么必须幂等**：错误会跨层向上传递，如果每层都重新包装，
最后看到的是"最外层、最不了解情况"的那一层的判断。
幂等保证**最早、最了解情况的那一层决定分类**。

配套：

- **Reporter**：写日志 + 按 Severity 决定是否推前端；同类错误（同 session+task+code+source）**5 秒窗口合并**，用 `count` 表达次数；
- **API 统一映射**：`writeError` 按 Code 映射状态码，未包装错误一律 500 + `internal error`，**不泄漏内部细节**；
- **上游修复**：把"门控丢失"这类无法处理的错误从根源消除——门控改为派生状态、自愈、永不返回错误。

**验证**：45 处 `_ =` 降到 32 处，剩余全部是通知类（`bus.Publish` / SSE 写入 / `Close`），并在代码中用集中注释说明约定。

### 3.7 持久化：双粒度建模 + 契约测试

**问题一：表结构怎么设计？**

ResearchState 有 6 个变长集合，其中 `Results` 必须支持**按 assignmentID 精确删除**（撤销）。

**决策标准**：

> **需要按元素级增删改 → 拆表；只需整体读写 → 集合类型列。**

| 集合 | 需求 | 决定 |
|---|---|---|
| Results | 按 assignmentID 精确删除 | **拆表** |
| Findings | 只追加，整体读 | 拆表 |
| CommitLog | 审计需按 op / 时间查 | 拆表 |
| History | 可能很长，前端分页 | 拆表 |
| Requirements | `[]string`，只追加 | **`TEXT[]`** |
| RelatedNodes | 嵌套结构，只读快照 | `JSONB` |

如果 `Results` 存成 JSON，撤销就要"读整个 JSON → 改 → 写回"，并发下极易丢更新。

**问题二：归属粒度不能统一。**

```
ResearchState  → 归属 Task      （跨 RunTask 存活，是研究的资产）
Assignment     → 归属 RunTask   （RunTask 消失即消失，是执行的产物）
```

这是业务语义决定的。统一成同一个外键，要么研究资产随执行一起被删，
要么执行的垃圾数据永久残留。

**问题三：怎么保证两套实现行为一致？**

**决策：契约测试（conformance tests）。**

```
internal/storage/storetest  ← 同一套断言
    ├── memory 实现跑一遍
    └── postgres 实现跑一遍
```

10 个子测试（Session/Task/RunTask/Assignment/Work/StateScalar/StateCommit/StateRevoke/Cascade/StateAlreadyExists），
任何一边改了语义，另一边立刻挂。`Capabilities` 用于声明已知差异（当前全为 false）。

**决策：并发用悲观锁而非乐观锁。**

```sql
SELECT id, version FROM research_states WHERE task_id = $1 FOR UPDATE
```

理由：写操作很短（几条 INSERT）、冲突本就少（聚合器单 goroutine 串行），
`FOR UPDATE` 语义简单、无需重试循环。乐观锁的优势场景是"写事务长、冲突多"，不适用。

**验证**：4 个并发测试 + `-race`，8 并发提交后 8 条证据全保留、版本号恰为 8。

## 五、面试时怎么讲（分层叙述）

### 30 秒版

> 一个多智能体深度研究系统。难点不是调用大模型，而是让一个跑几十轮、
> 有并发子任务、随时会被打断的系统在状态上始终正确。
> 我主要解决了三件事：把"本轮结束"和"研究结束"明确拆开、
> 定义了撤销与提交竞争时的先后语义、以及用契约测试保证内存和 PostgreSQL
> 两套存储行为完全一致。

### 2 分钟版

> **背景**：想做能真正"做研究"的 Agent，而不是一问一答。这意味着一次研究要跑几十轮、
> 并行多个子任务、还要能中断恢复。现有的 Runner 模式是一次性的，所以我换成了
> Eino 的 TurnLoop。
>
> **最难的是状态语义**。一开始我把"模型这轮说完了"当成结束，结果派发完子任务后
> 模型没话说，系统就退出了，子任务的结果再没人汇总。所以我明确拆成两种状态：
> 本轮结束只是回到空闲、RunTask 保持 running；只有模型主动调 `finish_research`
> 才进入终态。光有"结果回来就叫醒"还不够——所有子任务都失败时没有任何结果，
> 所以我又加了"全部终结唤醒"。
>
> **第二难的是并发**。撤销和提交可能同时发生，我的做法是"先标记后拦截"：
> 撤销先无条件记录，提交侧在锁内再检查。顺序颠倒就会出现"用户撤销了但证据还在"。
>
> **第三是数据**。研究状态有 6 个变长集合，我用一个标准决定拆表还是用集合类型：
> 需要按元素增删的拆表（撤销要按 assignmentID 精确删证据），只整体读写的用
> JSONB / TEXT[]。归属粒度也做了区分：研究资产归 Task、执行产物归 RunTask。
>
> **结果**：10781 行生产代码、8242 行测试（43%），247 个测试函数，
> 端到端验证 PG 模式下重启后数据完整保留。

### 5 分钟版

在 2 分钟版基础上补充：

1. 三级流水线（Scheduler / WorkPool / ResultAggregator）的职责划分与背压设计；
2. 真并行的实现（工厂模式，每个 Work 独立 Agent + 独立 ctx + 工具白名单）；
3. 错误分层（6 层 × 4 级 + 幂等 Wrap + 5 秒合并）；
4. 契约测试的具体形式与它抓住的问题；
5. 三个"只有跑起来才能发现"的 bug（无限派发、事件漏订阅、全终结不唤醒）。

## 六、最能体现深度的问题（准备被追问）

### 为什么把"本轮结束"和"研究结束"分开这么重要？

因为 Agent 的典型工作模式是"派发 → 等待"。如果用"模型没话说了"判断结束，
那么在派发子任务后模型确实无话可说，系统就会误判结束退出，
**子任务的结果永远无人汇总**。这个 bug 在单轮 demo 里完全看不出来。

### 撤销和提交并发时，为什么"先标记后拦截"能work？

因为标记是无条件的、且在锁内；任何晚于标记的提交都会看到标记。
反过来如果先查询再标记，查询和标记之间存在窗口，
提交可以在这个窗口里"合法"通过。**顺序本身就是同步原语。**

### 契约测试解决了什么实际问题？

解决了"实现漂移"。我在写 PG 实现时**照搬了内存实现的一个缺陷**
（Turn 用 Results 数量算而非 Findings），因为"对齐旧实现"是当时的指导原则。
契约测试把两边锁在同一批断言上，任何漂移立刻暴露。
这件事让我意识到：**对齐旧实现 ≠ 语义正确**。

### 为什么不用乐观锁？

写操作短（几条 INSERT）+ 冲突少（聚合器单 goroutine 串行），
`FOR UPDATE` 更简单、无需重试循环。乐观锁适合"长事务 + 高冲突"。

### 这个项目最难的一点是什么？

**是判断"什么是对的"，而不是"怎么写代码"。**
比如"门控丢失该不该报错"——最初当成错误处理，后来想明白了：
门控是派生状态，可以从 RunTask 状态推导出来，所以它应该自愈而不是报错。
这类判断没有标准答案，需要回到业务语义去想。

## 七、一句话总结（可放简历开头）

> 用 10.8k 行生产代码与 8.2k 行测试，实现了一个在**状态语义、并发一致性、
> 数据持久化**三个维度上都可验证的多智能体系统——重点不是"能跑"，
> 而是"边界明确、错误可观测、换存储不改变行为"。
